Documentation

Tout ce qu'il faut savoir pour lancer le projet en local et ajouter un nouveau jeu dans les règles de l'art.

Structure du repo

Les pages du site (accueil, à propos, documentation...) partagent un même en-tête et un même design système, définis une seule fois dans assets/. Chaque jeu vit dans le dossier de son développeur, sous games/ : un dossier par développeur, un fichier HTML autonome par jeu. La liste des jeux affichée sur le site est générée automatiquement à partir de ces fichiers, elle n'est jamais écrite à la main.

gamAa/

Lancer le projet en local

Aucune installation nécessaire pour naviguer sur le site : clone le dépôt et ouvre index.html directement dans un navigateur, ou lance un petit serveur local pour naviguer confortablement entre les pages. Node.js n'est requis que pour régénérer assets/games.js après l'ajout d'un jeu (voir ci-dessous).

Ajouter un nouveau jeu

1. Duplique le dossier games/_template/ et renomme la copie avec ton nom : games/ton-nom/.

2. Renomme mon-jeu.html avec le nom de ton jeu, puis modifie le <title>, les balises <meta name="game:*"> et le code à l'intérieur. Ces informations sont ce que la liste des jeux affiche sur l'accueil.

Le classement partagé et la connexion sont facultatifs. Le template les inclut par défaut (voir la carte suivante), mais rien ne t'oblige à les garder : tu peux supprimer les balises <script> Supabase et le bloc .leaderboard de ton fichier, ton jeu reste parfaitement valide sans. Même si tu les gardes tels quels, ton jeu fonctionne normalement — seul le classement ne s'affiche pas tant que Supabase n'est pas configuré.

3. Remplis profile.json dans ce même dossier : ton nom, une courte bio et tes liens (GitHub, site, réseaux). C'est ce qui apparaît sur ta fiche de la page Communauté. Un champ vide n'est simplement pas affiché.

4. Ouvre ta pull request en ne touchant que ton dossier games/ton-nom/. Ne commite jamais assets/games.js toi-même : c'est un fichier généré, partagé par tout le monde, et le modifier dans ta PR provoquerait un conflit avec les autres contributions. Une CI GitHub Actions le régénère automatiquement dès que ta PR est mergée sur main — et une seconde CI rejette toute PR qui y toucherait. Tu peux quand même lancer node scripts/build-games.js en local juste pour vérifier l'aperçu, sans committer le résultat. Le dossier games/_template/ lui-même est toujours ignoré par le script (tout dossier commençant par _ l'est).

Le fichier profile.json

Un seul fichier par développeur, à la racine de ton dossier games/ton-nom/. Facultatif — sans lui, ta fiche Communauté affiche juste le nom renseigné dans game:dev et la liste de tes jeux.

{
  "name": "Ton Nom",
  "bio": "Une phrase pour te présenter.",
  "links": {
    "github": "https://github.com/ton-pseudo",
    "site": "",
    "twitter": "",
    "linkedin": ""
  }
}

Classements et connexion optionnelle

gamAa reste un monde libre : on joue sans compte. Mais chaque jeu peut proposer un classement partagé (top scores, tous joueurs confondus) et une connexion facultative pour qu'un joueur retrouve son meilleur score d'une session à l'autre au lieu d'en créer un nouveau à chaque partie. Ça repose sur Supabase (base de données + authentification hébergées), inclus via une simple balise <script> — toujours sans framework ni build.

Le dossier games/_template/ intègre déjà tout le nécessaire (widget de connexion, appel Leaderboard.submitScore() à la fin de la partie, affichage du classement) : si tu pars de ce modèle, tu n'as rien à faire de plus pour en profiter. Mais rien n'est obligatoire : tu peux retirer ce bloc si tu ne veux pas de classement pour ton jeu, ce n'est pas une condition pour que ta pull request soit acceptée.

Pour que ça fonctionne réellement, un projet Supabase doit être configuré une fois pour tout le site :

1. Crée un projet gratuit sur supabase.com.

2. Dans l'éditeur SQL du projet, exécute le contenu de supabase/schema.sql (crée la table scores et ses règles d'accès).

3. Dans assets/supabase-config.js, remplace SUPABASE_URL et SUPABASE_ANON_KEY par les valeurs de Project Settings > API. La clé "anon" est faite pour être publique côté client, ce n'est pas un secret.

4. Dans Authentication > URL Configuration, renseigne le Site URL avec l'adresse réelle du site déployé (ex. https://ton-site.vercel.app) et ajoute-la aussi aux Redirect URLs avec un joker (ex. https://ton-site.vercel.app/**) pour couvrir toutes les pages de jeux. Sans ça, le lien magique envoyé par email redirige vers une mauvaise adresse et la connexion échoue.

Tant que ce fichier garde ses valeurs par défaut, les jeux restent jouables normalement : seul le classement est indisponible (erreur silencieuse en console).

// assets/leaderboard.js expose :
Leaderboard.getCurrentUser()                  // -> Promise<user | null>
Leaderboard.onAuthChange(callback)
Leaderboard.signInWithEmail(email)            // envoie un lien magique, pas de mot de passe
Leaderboard.signOut()
Leaderboard.submitScore(gameSlug, name, score)
Leaderboard.getTopScores(gameSlug, limit)     // meilleur score par joueur ; sans limit, renvoie tout le classement

La base ne garde qu'un score par joueur dans le classement (le meilleur), et personne ne peut modifier ou supprimer le score de quelqu'un d'autre — les règles d'accès (supabase/schema.sql) l'interdisent au niveau de la base, pas seulement dans le code. Un score anonyme reste basé sur un pseudo libre : sans connexion, rien n'empêche quelqu'un de le falsifier.

Le périmètre de cette base est volontairement limité aux scores. La seule table créée par supabase/schema.sql est scores (jeu, pseudo, score, date, et l'identifiant de compte si connecté) : pas de profil joueur, pas de suivi de navigation, pas de collecte au-delà de ce qui sert le classement. La connexion facultative passe par le système d'authentification intégré de Supabase (juste pour relier un score à un compte), gamAa ne stocke ni ne voit jamais de mot de passe.

Le composant d'en-tête

Toutes les pages du site (hors jeux) affichent le même en-tête via un seul composant partagé : assets/header.js. Chaque page pose juste un <div id="site-header"></div> suivi du script, et le lien actif du menu est détecté automatiquement d'après l'URL. Le style commun (en-tête, boutons, cartes) vient de assets/site.css, chargé sur chaque page. Pour créer une nouvelle page de site, copie ce bloc et n'ajoute que le CSS propre à ta page.

<link rel="icon" type="image/png" href="assets/icon.png" />
<link rel="stylesheet" href="assets/site.css" />
...
<div id="site-header"></div>
<script src="assets/header.js"></script>

Template de base pour un jeu

Ce squelette est exactement celui de games/_template/mon-jeu.html : duplique ce fichier plutôt que de recopier le code ci-dessous à la main. Un jeu reste un fichier HTML autonome (CSS et JS inclus) : il ne dépend pas du header du site. Les balises <title> et <meta name="game:*"> sont ce que scripts/build-games.js lit pour générer la fiche du jeu sur l'accueil : renseigne-les avec soin.

<!DOCTYPE html>
<html lang="fr">
<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  <link rel="icon" type="image/png" href="../../assets/icon.png" />
  <meta name="game:type" content="Arcade" />
  <meta name="game:description" content="Une phrase courte qui donne envie de jouer." />
  <meta name="game:dev" content="Ton Nom" />
  <meta name="game:date" content="JJ/MM/AAAA" />
  <title>Nom du jeu</title>
  <style>
    * { margin: 0; padding: 0; box-sizing: border-box; }
    body {
      font-family: "Segoe UI", Roboto, Arial, sans-serif;
      background: #1c2b39;
      color: #fff;
      min-height: 100vh;
      display: flex;
      flex-direction: column;
      align-items: center;
      justify-content: center;
    }
    /* ... styles du jeu ... */
  </style>
</head>
<body>
  <h1>Nom du jeu</h1>
  <div id="gameWrap"><!-- canvas ou DOM du jeu --></div>

  <script>
    // logique du jeu, tout en JavaScript natif
  </script>
</body>
</html>

Charte graphique

Navy — #1c2b39
Ambre — #f4b400

Typographie : police système (Segoe UI, Roboto, Arial, sans-serif), pas de police externe à charger.

Règle de simplicité visuelle : peu d'éléments à l'écran, priorité à la lisibilité et à la jouabilité immédiate. Pas d'emoji, design flat, sans ombres superflues.
